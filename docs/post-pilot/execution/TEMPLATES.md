## 1. Deliverable and boundaries

Ship exact legacy version pins first; then ADMIN/assigned-SUPPORT authoring of supported renderer inputs, ADMIN publication, organization-private customer templates, tenant-safe previews and explicit invitation adoption. Existing DRAFT, PUBLISHED and CLOSED invitations all pin their migration baseline. Publishing a template never rewrites an invitation. Publication and retirement change only future selection; an already pinned invitation can still be edited and rendered with its immutable version.

F44 requires the common organization resolver interface, which can be implemented while `OrganizationMembership.userId` remains unique. It does **not** require F38 multi-membership activation, corporate contracts, sales, payments, bank credentials or fiscal decisions. F39 conversion consumes the existing/new transaction-aware Events creation seam; F44 owns changing that seam to select and pin versions. No F44 implementation imports an enquiries service.

Core F44 does not create corporate `BrandVersion`, contract acceptance, commercial print proofs or printer integration. A later brand adoption flow uses the same explicit preview/confirmation contract, with its own immutable brand pin and source hash. Existing guest attendance, acknowledgement statements, captured invitation lifetime, ticket validity and fixed export snapshots retain their present semantics. A template edit is never a reason to republish an event, reset lifetime, resend invitations or regenerate an accepted export/proof.

These facts establish **specific integration gaps**, not permission to reinterpret old data.

Decision: migration pins and serializes legacy data verbatim, with capability provenance `LEGACY_UNVERIFIED`; it does not rewrite legacy variants/palettes/fonts to compensate. Legacy pilot rendering continues under its existing acceptance gates. Newly authored publication is closed until a reviewed capability manifest is integrated with the deployed frontend and four-language acceptance. Engineering can implement draft CRUD and JSON previews meanwhile. The UI must label payload-only previews honestly; no response claims that a browser render passed merely because JSON validation passed.

Create `backend/src/modules/design/templates/capabilities/legacy-catalogue.ts` from the actual current seed declarations as an initial backend **ceiling**, without treating those names as tested renderer support. Create a checked-in manifest contract in `docs/contracts/invitation-renderer-capabilities.schema.json` and approved manifests under `docs/contracts/invitation-renderer-capabilities/`. A manifest contains renderer key, immutable capability version, schema version, frontend build/revision, digest, supported block/default/variant map, accepted theme keys, font IDs and immutable bundled font metadata, palette-role mappings, permitted media slots, and locales. It is deployed configuration reviewed with code, never an ADMIN-editable whitelist or an uploaded draft field.

For new drafts, structural validation uses the backend ceiling. For publication, the allowed set is the intersection of that ceiling and the exact tested frontend manifest. A string newly added to draft `blockVariants`/fonts/renderer key cannot broaden either set. Initially a seed-only variant with no frontend handler cannot be published; null/default variants may be used where explicitly manifested. Real frontend variants in the table are evidence for a future reviewed ceiling alignment, **not automatically enabled by this plan**. New block/layout code or new font delivery requires frontend implementation and a reviewed manifest/code deployment.

Manifest integration must also define named palette roles, rather than inventing a role for positional legacy `colors`. For new capabilities only, `buildInvitationContent` adds `resolvedTheme: { headingFont, bodyFont, palette: { name, roles } }` using the manifest's exact role mapping; frontend renders that contract. Legacy response fields and values remain unchanged. New manifests may restrict new custom-color cardinalities when their role map requires it, with field errors. Existing legacy themes retain existing validation/serialization. Do not guess that the first color is a background across both seed families. Unknown theme keys, CSS, HTML, executable SVG, remote font/image URLs, script, arbitrary settings/layout code and manifest self-registration are rejected in new authoring input.

Frontend implementation requests are concrete: add `capabilities.ts`/manifest export and tests to its renderer, wire tested palette-role and bundled font inputs, handle explicit capability identities and fail closed on unknown new capabilities, add a noninteractive preview mode (no reply forms, trackers or external navigation), add fr resources/negotiation, and add visual fixtures at mobile/desktop widths in en/ru/fr/hy, long text and Armenian/Cyrillic glyph coverage. These belong on the frontend branch/integration flow; they are not source changes to be guessed into this backend checkout. Backend must expose exact synthetic fixtures for those tests.

## 3. Schema and database invariants

Use additive Prisma models plus handwritten forward migrations for CHECKs, partial indexes and immutable-state triggers. Keep legacy render columns on `DesignTemplate` for deployment compatibility, frozen after baseline capture; final application code reads them only in the migration adapter. Do not drop them in this stream.

### Identity, ownership and versioning

- `DesignTemplate`: existing `id/key/name/isActive` remain. Add nullable `organizationId` FK to `Organization` with RESTRICT; `null` means shared. Add non-null `ownerScopeKey`, constrained to exactly `shared` when organization is null, otherwise `org:` concatenated with organization ID. Add nullable `activeVersionId`, `revision Int default 1`, `nextVersionNumber Int default 2`, and `retiredAt`. Keep `key @unique` globally; customer-private keys are generated opaque `private-<uuid>`, not customer-identifying names or colliding semantic keys. Shared keys retain existing values. Add unique `(id, ownerScopeKey)`; index `(ownerScopeKey, isActive, name, id)` for scoped catalogue pages.
- `DesignTemplateVersion`: `id`, `templateId`, `ownerScopeKey`, `versionNumber`, `name`, exact `allowedFonts String[]`, `palettes Json`, `supportedBlocks BlockType[]`, `blockVariants Json`, `defaultTheme Json`, `schemaVersion`, `rendererKey`, nullable `capabilityVersion`/`capabilityDigest`, `assetManifest Json default []`, `contentHash`, `provenance` (`LEGACY_BASELINE`, `SEED_RELEASE`, `AUTHORED`), `recordedAt`, nullable `publishedAt`/`publishedByUserId`, nullable `sourceDraftId`/`sourceDraftRevision`. Legacy publication metadata stays null. `recordedAt` means when imported, not past publication. Composite FK `(templateId, ownerScopeKey) → DesignTemplate(id, ownerScopeKey)`, unique `(templateId, versionNumber)`, unique `(id, templateId, ownerScopeKey)`. `DesignTemplate.activeVersionId` is a same-template/scope composite FK to this table. Every version row is immutable, including its hash, name and render fields; reject UPDATE/DELETE with a trigger. Version availability is separate.
- `DesignTemplateVersionAvailability`: `(versionId PK, templateId, ownerScopeKey)`, `canSelect Boolean`, `retiredAt`, `retiredByUserId`; composite FK to version. `canSelect=false` forbids new selection only. No FK cascade deletes immutable history. Catalogue uses active pointer + this row + template active state. Re-activating a previously published version is an ADMIN-only explicit active-pointer operation; it never changes consumers.
- `DesignTemplateDraft`: `id`, `templateId`, `ownerScopeKey`, nullable `basedOnVersionId`, `revision Int default 1`, `state EDITING|READY_FOR_REVIEW|PUBLISHED|DISCARDED`, render fields matching a version, `contentHash`, timestamps, `createdByUserId`, `updatedByUserId`, nullable `publishedVersionId`. One open draft per template via partial unique index on templateId WHERE state IN ('EDITING','READY_FOR_REVIEW'). Composite ownership and same-template version FKs. Draft EDITING is mutable through expected revision. READY_FOR_REVIEW can return to EDITING; any edit clears current validation/review/preview acceptance and increases revision. Published/discarded draft content freezes; edit by cloning. Valid state shape checks require publishedVersionId iff PUBLISHED.
- `DesignTemplateAuthorAssignment`: `templateId`, `ownerScopeKey`, `supportUserId`, `assignedByUserId`, `assignedAt`, nullable `revokedAt`; composite template FK, user FKs RESTRICT; partial unique `(templateId,supportUserId) WHERE revokedAt IS NULL`; index `(supportUserId,revokedAt,templateId)` for assigned work list. A DB trigger checks assignee is currently active SUPPORT at assignment; service rechecks current role/active status on every access and every committing action. Revocation and assignment audit happen in one transaction. Role demotion immediately denies access even while a historical assignment row remains.
- `DesignTemplateValidation`: immutable result for `(draftId,draftRevision,contentHash,capabilityDigest)`, schema result, field errors, compatibility result, timestamps. Unique on that tuple. No user-supplied success flag. No fabricated browser-render success; manifest acceptance evidence belongs to the reviewed renderer release.
- `DesignTemplatePreview`: `id`, draft or target-version FK, `templateId/ownerScopeKey`, requesting user, exact revision/hash/capability digest, `previewSource SYNTHETIC|EVENT`, nullable eventId/invitationId/designRevision/sourceHash, `payloadHash`, `createdAt`, `expiresAt`, `consumedAt`. Store identity/hashes, not event payload or guest content. Bounds: 15-minute confirmation lifetime. Every read/confirmation rechecks current authorization. User supplied hashes alone confer nothing.
- `DesignTemplatePublication`: `id`, `templateId`, `ownerScopeKey`, `requestedByUserId`, UUID `idempotencyKey`, `requestHash`, draft/revision/hash, resulting versionId, `createdAt`; unique `(templateId,idempotencyKey)`. Store the receipt in the same transaction as version insertion/pointer move/draft freeze. Hash includes the actor and all intentional request fields so another payload or actor cannot replay a key.
- `DesignTemplateAudit`: append-only transactionally written minimal action facts (actor userId, template/scope, draft/version IDs, revision/hash, action/time); no copied name/email, private preview payload, tokens or arbitrary comments. Do not rely on fire-and-forget Mongo audit for author assignment/publication correctness.

A version's complete immutable serialization includes identity key/name, renderer/capability, theme constraints/defaults and ordered asset manifest. Hash new content via one canonical JSON function (UTF-8 sorted object keys, preserved arrays, normalized dates) in `template-content.ts`; hash is not a substitute for DB immutability. Legacy `contentHash` uses a separately declared `legacy-jsonb-v1` representation so SQL can compute `md5(jsonb_build_object(...)::text)` without requiring pgcrypto. It is an integrity checksum, not a credential or claim of cryptographic security. The new SHA-256 hash algorithm is stored explicitly (`contentHashAlgorithm`) on every record; never compare unlike algorithms or rewrite baseline hashes later.

### Invitation tenant and version pins

Add nullable first, later NOT NULL:

- `Invitation.organizationId` denormalizes the event owner, with composite FK `(eventId,organizationId) → Event(id,organizationId)`; add unique Event `(id,organizationId)`. No event movement between organizations is introduced; changing an owner organization with invitations must be an explicit future migration/transfer, not an UPDATE that bypasses private-template ownership.
- `Invitation.templateVersionId` and `templateOwnerScopeKey`; composite FK `(templateVersionId,templateId,templateOwnerScopeKey) → DesignTemplateVersion(id,templateId,ownerScopeKey)`.
- CHECK `templateOwnerScopeKey='shared' OR templateOwnerScopeKey='org:'||organizationId`. This gives real tenant constraints even for raw SQL; nullable composite FKs alone do not prove tenant equality. Add `(templateVersionId)` index for reference checks and `(templateId,templateVersionId)` for pinned/version inventory. Existing eventId/templateId indexes remain as actually queried.
- `Invitation.designRevision BigInt default 1` with CHECK >0. Expose as decimal string. A narrowly defined DB trigger bumps it when fields in the upgrade source (theme/pin/blocks, published guest-facing event details, venues/timeline, RSVP display configuration/questions or materialized template assets) change. Invitation metadata/lifetime or attendance-only changes do not reset the design pin. Ensure no recursive bump on designRevision-only updates. Trigger updates are transactional and serve both ordinary code and raw SQL/worker writes.
- `InvitationTemplateAdoption`: immutable receipt with invitationId/eventId/organizationId, actor, UUID idempotencyKey, requestHash, source/target version IDs, previewId, before/after designRevision/sourceHash, appliedAt; unique `(invitationId,idempotencyKey)`, composite event/org and version ownership FKs. Record only design transition metadata, not guest data or copied blocks.

Use table CHECKs for required publication provenance: AUTHORED must have publishedAt/publishedBy/sourceDraft/revision/capability; LEGACY_BASELINE must not claim those. `SEED_RELEASE` records a deployment release identity with nullable human actor and no invented review. New immutable seed releases need the same capability approval before becoming active; existing legacy baselines remain selectable under their current pilot behavior.

### Asset ownership and reference ledger

Implement raster template artwork only in core: private PNG/JPEG/WebP, nonanimated, sanitized/reencoded metadata-free. No font, SVG, HTML, PDF, AUDIO or remote URL upload. Current renderer can consume raster media through existing HERO/GALLERY media arrays; declare only those slots when the reviewed manifest confirms them. Absence of a declared slot means nonempty asset input is rejected, not silently rendered as a new background/layout.

- `DesignTemplateAsset`: id/templateId/ownerScopeKey, kind PHOTO|COVER, processing state, source and sanitized-object ledger keys, dimensions/size/mime/hash, createdBy/at. Composite template FK and unique `(id,templateId,ownerScopeKey)`.
- `DesignTemplateDraftAsset`: normalized ordered references `(draftId,templateId,ownerScopeKey,slot,position,assetId)` with composite FKs to draft and asset, unique `(draftId,slot,position)` and `(draftId,slot,assetId)`. Do not put unvalidated unscoped IDs only in JSON arrays.
- `DesignTemplateVersionAsset`: immutable equivalent referencing version and same-owner sanitized asset; asset manifest/hash records ordered immutable content hash/dimensions/slot, not private storage keys or URLs. Shared and org-private ownership cannot be changed after any draft/version reference exists. No private-to-shared promotion endpoint; cloning private into shared is refused. Shared-to-private clone copies sanitized artwork into new private-owned asset rows/objects using the ledger, not a foreign source ID.
- `DesignTemplateStoredObject`: random UUID key accepted by `PrivateStorageService`, nullable templateId/assetId/materializationId, purpose SOURCE|SANITIZED|EVENT_COPY, state RESERVED|AVAILABLE|RETIRED|DELETED, processing lease owner/expiry/generation, cleanupAfter, deletedAt, checksum/size. Row survives owner deletion as a tombstone. Index `(state,cleanupAfter,key)` for cleanup and `(leaseUntil,createdAt)` for processing. Never repurpose `ExportArtifact`; their lifetimes differ.
- `InvitationTemplateAsset`: event/invitation/org IDs and pinned template/version scope, source version-asset ID, slot/position, unique materialized private object key, checksum; composite event/org and pin ownership constraints. A deferred constraint trigger checks its version equals the invitation's final selected version at commit; whole upgrade swaps bindings atomically. Reference old copies only while their invitation/preview receipt still needs them. No cross-event copy is attached merely because bytes/hash match.

No public template source URLs are minted, even for published private versions. Author/preview routes serve source/sanitized files only through authenticated resource checks with `private, no-store` and recheck authorization after storage.get. Shared published artwork can later have an explicitly public distribution policy; it is not needed here.

For an event's adopted artwork, preserve source privacy through event-owned **private** materialization and authorized file routes. Do not copy it into today's public `MediaAsset` store. New guest file paths are `GET /invitations/:slug/design-assets/:assetId/file` for otherwise-readable generic PUBLIC/UNLISTED pages and `GET /invitations/:slug/g/:guestToken/design-assets/:assetId/file` for personal capability access. They run the same live status/expiry/visibility/token checks as `InvitationsService.pageMeta`, check the materialization belongs to this invitation's pinned version, read bytes, and repeat authority/pin checks before returning. An authenticated editor uses `GET /events/:eventId/design-assets/:assetId/file` with invitation:read. Return 404 for invalid/revoked/foreign materialization and no redirects/presigned storage URLs. Existing capability-route log redaction must cover these paths.

The shared cached JSON contains only noncredential internal design-asset descriptors; `servePage()` projects them to authorized event file paths **after** shared-cache retrieval, for the specific generic/personal request. Never put a guest token into the shared cache or a catalogue response. `buildInvitationContent` uses version default media only when that block has no explicit event upload override; override removal reveals its documented default, and disabling a block hides both. It never removes/replaces the host's assetIds. Synthetic previews use authenticated template-source routes; event previews use authenticated event/draft routes. A private customer's template key/name and other unused artwork are never exposed through another tenant's catalogue or event preview. An event intentionally published PUBLIC/UNLISTED exposes only the artwork it actually uses, under that event's existing visibility promise.

### A. Expand / capture (authoring and divergent publication off)

1. Add version/scope/pin columns nullable, new empty tables and nonblocking/NOT VALID constraints where appropriate. For existing DesignTemplate, ownership defaults to shared; no legacy organization ownership is invented. Add Event composite unique and version unique keys before dependent FKs. Existing indexes are kept. For large production populations, create covering unique indexes with CONCURRENTLY in an explicitly nontransactional pre-step, then attach constraints; do not paste CONCURRENTLY into a transactional migration.
2. Brief transaction locks `design_templates` against render-data updates/inserts while baseline rows and pointers are captured; install an INSERT-only legacy bootstrap trigger and a render-field freeze trigger in that transaction. Production old seed `update:{}` remains safe; old development reseeding with changed fields is deliberately refused until its adapted seed code deploys. No template authoring endpoint currently exists, so this does not disable an authorized customer editor. Lock templates before invitations consistently.
3. Capture **all** templates, active/inactive and used/unused. Deterministic baseline id `dtv_legacy_` concatenated with existing id; `versionNumber=1`; copy every stored render field verbatim, including empty arrays, odd keys, legacy `font`/`primary`, JSON nulls and array ordering. Copy name/key facts; do not normalize fonts/palette objects or call validateTheme during capture. `recordedAt=transaction_timestamp()`, `publishedAt/publishedBy/sourceDraft=NULL`, `provenance=LEGACY_BASELINE`, `rendererKey='legacy-generic'`, capability fields NULL, assetManifest `[]`. Record checksum algorithm explicitly. Set activeVersionId to baseline even when isActive=false; availability canSelect mirrors previous isActive.
4. During compatibility only, INSERT of a legacy DesignTemplate captures its immediate exact baseline with honest LEGACY_BASELINE provenance. Invitation BEFORE INSERT/UPDATE-of-templateId trigger supplies the matching baseline pin/scope/org only when old code omitted the new fields or switched templateId without a matching new pin. It must NOT replace an explicitly supplied valid version. This prevents old creation/switch paths leaving gaps during rolling deployment. Authoring remains disabled, so active divergent versions cannot exist yet.
5. Backfill invitation rows in bounded primary-key batches, committing each (e.g. 1,000 rows), deriving organization from the event and baseline from the **current stored** templateId. A concurrent switch takes row locks; the compatibility trigger updates both pins, so it cannot produce a stale pair. Do not infer an original template from publication timestamps: only the current legacy state is knowable.

SQL outline (expand DDL omitted only for readability; implement constraints above in the generated-and-reviewed migration):

```sql
INSERT INTO design_template_versions
  (id,"templateId","ownerScopeKey","versionNumber",name,"allowedFonts",palettes,
   "supportedBlocks","blockVariants","defaultTheme","schemaVersion","rendererKey",
   "capabilityVersion","capabilityDigest","assetManifest","contentHashAlgorithm",
   "contentHash",provenance,"recordedAt","publishedAt","publishedByUserId")
SELECT 'dtv_legacy_'||t.id,t.id,'shared',1,t.name,t."allowedFonts",t.palettes,
       t."supportedBlocks",t."blockVariants",t."defaultTheme",1,'legacy-generic',
       NULL,NULL,'[]'::jsonb,'legacy-jsonb-v1',
       md5(jsonb_build_object('key',t.key,'name',t.name,'allowedFonts',t."allowedFonts",
           'palettes',t.palettes,'supportedBlocks',t."supportedBlocks",
           'blockVariants',t."blockVariants",'defaultTheme',t."defaultTheme")::text),
       'LEGACY_BASELINE',transaction_timestamp(),NULL,NULL
FROM design_templates t
ON CONFLICT ("templateId","versionNumber") DO NOTHING;

WITH batch AS (
  SELECT i.id FROM invitations i
  WHERE i."templateVersionId" IS NULL OR i."organizationId" IS NULL
  ORDER BY i.id FOR UPDATE SKIP LOCKED LIMIT 1000
)
UPDATE invitations i SET "templateVersionId"='dtv_legacy_'||i."templateId",
       "templateOwnerScopeKey"='shared',"organizationId"=e."organizationId",
       "designRevision"=COALESCE(i."designRevision",1)
FROM batch b, events e WHERE i.id=b.id AND e.id=i."eventId";
```

Baseline equality queries before any divergent version is allowed:

```sql
SELECT count(*) AS missing_or_mismatched_pin
FROM invitations i JOIN events e ON e.id=i."eventId"
LEFT JOIN design_template_versions v ON v.id=i."templateVersionId"
WHERE v.id IS NULL OR v."templateId"<>i."templateId"
   OR i."organizationId" IS DISTINCT FROM e."organizationId"
   OR i."templateOwnerScopeKey" IS DISTINCT FROM v."ownerScopeKey";

SELECT t.id FROM design_templates t
JOIN design_template_versions v ON v."templateId"=t.id AND v."versionNumber"=1
WHERE ROW(t.name,t."allowedFonts",t.palettes,t."supportedBlocks",t."blockVariants",t."defaultTheme")
 IS DISTINCT FROM ROW(v.name,v."allowedFonts",v.palettes,v."supportedBlocks",v."blockVariants",v."defaultTheme");

SELECT count(*) AS fabricated_authorship FROM design_template_versions
WHERE provenance='LEGACY_BASELINE' AND ("publishedAt" IS NOT NULL
 OR "publishedByUserId" IS NOT NULL OR "sourceDraftId" IS NOT NULL);

SELECT t.id FROM design_templates t LEFT JOIN design_template_versions v
 ON v.id=t."activeVersionId" AND v."templateId"=t.id AND v."ownerScopeKey"=t."ownerScopeKey"
WHERE v.id IS NULL;
```

All counts/result sets must be zero; also require `count(versions WHERE provenance='LEGACY_BASELINE')=count(legacy templates at capture plus compatibility inserts)`. Backfill may advance cache revisions because rows changed, but it must not alter any rendered value, status, RSVP, lifetime or existing export bytes.

### C. Constrain / contract (then permit divergent publication)

After fallback metric is zero and verification queries pass, VALIDATE composite FKs/CHECKs, set pins/org/scope/designRevision NOT NULL, remove legacy invitation auto-pin and legacy template bootstrap triggers, and keep render-column freeze/immutable version triggers. New inserts into stable template identity go through the authoring/seed transaction and carry a draft or valid version; private identity fields/key/scope cannot be changed to turn a tenant template into shared content.

In a fresh forward migration remove `guest_page_change` and `guest_payload_change` triggers from `design_templates` once no guest reader uses mutable columns. Keep all existing invitation/event/block/question/media triggers. Published versions need no fan-out trigger because UPDATE/DELETE is denied. Draft/assignment/publish/availability tables must not emit guest revision changes. Adoption writes the invitation and affected block/binding rows, so existing ledgers change atomically; Redis SCAN invalidation is best effort. The designRevision triggers are additional narrowly scoped fences, not a replacement for shared/personal guest ledgers. The current corrected payload trigger alias is preserved.

Run the invariant queries after constraint validation, then allow authoring gates. A rollback can disable authoring, publishing or adoption. After two divergent published versions exist, rollback to code ignoring pins is forbidden. Keep the compatible pinned-reader release as the minimum rollback target; roll forward on migration faults. Never overwrite baseline rows, downgrade the schema, unpin invitations or delete referenced objects to simulate rollback.

`X-Aveline-Organization-Id` is an optional scalar opaque selector of 1–64 characters, not authorization. Event-scoped calls derive the actual event organization and preserve direct event-only DESIGNER access even with null organizationRole; after checking current resource permissions, a conflicting header returns 409 `ORGANIZATION_CONTEXT_MISMATCH`. ADMIN authoring a private template uses an explicit validated org selector through `platformPermission`; SUPPORT gets no generic organization browsing authority. Global shared authoring requires no tenant header; reject a conflicting private selector rather than silently changing the target. Resource identity owns the scope on subsequent template/draft/version/asset routes.

Add permissions `template:author`, `template:publish`, `template:assign`, `template:catalogue-manage` to `ALL_PERMISSIONS` and `PLATFORM_ONLY`. ADMIN has all. SUPPORT has only `template:author`, and service policy narrows it to a current explicit per-template assignment. Author access includes reading/editing/uploading/validating/previewing/submitting an assigned draft and cloning a new draft **within that same template**; it never permits creating a new shared/private identity, changing ownership, assigning others, publishing, retiring or moving an active version. ADMIN creates identities and assigns SUPPORT. An event DESIGNER/OWNER/org OWNER/manager with no platform authority has no author permission, even for its organization; they can select authorized published templates and customize their event as today. Customer template requests are fulfilled by the ADMIN workflow.

Do not confuse this assignment with broad existing SUPPORT event powers or sales enquiry assignment. Authoring assignment alone grants synthetic preview and that template's assets. A real-event preview additionally requires current event invitation:read, same target organization for a private template, and the normal event-content projection. It exposes no contacts, guest names/tokens/households/private contributions, internal venues/timeline, contract or billing records. Shared-template support assignment grants no cross-tenant event read through the template service.

Every committing service operation re-resolves active user/platform status, assignment, org deletedAt and target ownership **inside** its transaction. Serialize template assignment changes with the template lock used for draft edits so revocation cannot race a successful post-revocation commit. For SUPPORT demotion/account closure take current `users` FOR SHARE late in the domain transaction before the final live actor recheck; role/deactivation updates take the conflicting row lock. The common order starts with Organization SHARE where present, then existing domain/event/invitation locks, then current User SHARE; never acquire an existing organization after taking a new user-prefix lock. Shared template authoring has no organization fence. Customer membership revocation uses Organization UPDATE but does not itself revoke an independent active staff author assignment. Account closure/role changes must not acquire a template lock after holding the User update lock; any assignment cleanup runs separately after the user state commits, with live user checks already denying access. Do not encode assignment or role authority in JWTs or Redis. Return 403 for an ungranted action on an otherwise visible author resource; return 404 for nonexistent/foreign/unassigned author resources and foreign private catalogue keys to avoid discovery. Existing event guard 403 behavior remains unless changed deliberately in its owning stream.

### Publication and draft race protocol

1. Perform bounded structural computation outside DB locks; no renderer process/network/storage inside a DB transaction. Compute exact immutable candidate hash, but recheck it under lock.
2. Transaction lock order: resolved Organization SHARE lifecycle fence (private only) → template UPDATE → draft → current User SHARE → sorted asset/reference rows → final live role/assignment/scope recheck and writes. Assignment/revoke uses the same template lock; acquire current User SHARE before adding user-referencing audit/assignment rows, whose FK checks otherwise take implicit user locks. Shared authoring omits the organization fence. Organization closure/membership changes acquire Organization UPDATE; use the org stream's helper rather than a copied lock. No User→existing-Organization inversion or platform-wide user-lock rewrite is introduced. If export privacy is ever relevant in a later consumer it precedes the organization fence; core F44 does not touch it.
3. Check existing publication dedupe receipt **before** stale-draft handling so a successful request retries successfully after its draft was frozen. Compare requestHash/actor; otherwise409. Lock draft, compare expected revision+hash, state, synthetic preview actor/hash/revision/capability/expiry, and deployed manifest digest; lock/version-source sanitized assets and reject pending/retired/foreign references. No storage work now.
4. Allocate number by locked `nextVersionNumber` (or conditional increment returning previous number), insert immutable version and normalized asset references, availability row, increment counter, move active pointer, increment template revision, freeze draft, consume preview, insert publication receipt and audit. All commit together. Unique template/version and template/dedupe keys defend races even if a caller misses an application check. A second publisher either returns its matching receipt or conflicts; it cannot publish different content under the same number.
5. No fan-out/guest cache invalidation/publication email is necessary. If a later notification is added, persist its intent in the same transaction; F44 does not send messages merely because templates changed.

Draft PATCH locks template/draft, checks current assignment and expectedRevision, merges omitted fields, validates whole aggregate and same-owner assets, replaces normalized supplied references, increments revision, clears current acceptance pointers and hashes final config. Concurrent edits to the same revision give one success/one409; edits to different templates proceed independently. Review/submit hash/revision races follow the same lock. No unbounded per-asset query loop; fetch/lock asset set once (max20).

### Artwork processing/materialization protocol

`POST …/:draftId/assets` accepts multipart raster file max5MiB plus kind, expectedRevision and UUID idempotencyKey; one file. Reserve private object ledger before put; return202 `{assetId,state:'PROCESSING'}`; `GET …/:draftId` batches processing state. Worker claims oldest eligible rows via SKIP LOCKED with bounded batch10, lease30sec/heartbeat10sec, max3 attempts, bounded image decoding (max16 million pixels, max8192 dimension, max1 page); strip metadata and reencode PNG/JPEG/WebP. Mark AVAILABLE only after checksum/object existence succeeds, checking lease ownership and current template assignment/scope on any user-sensitive completion. Original source cleanup after successful sanitization plus one-hour safety window; failed/stale originals temporary only. Store dimensions/mime of emitted output, not uploaded claims.

Attach/remove reference requires expected draft revision, same template/scope and AVAILABLE asset. Deleting an asset locks its row and refuses if immutable version references exist; draft reference removal is explicit and transactional. Worker state may mutate while processing; AVAILABLE sanitized identity/hash cannot mutate once referenced by a version. New bytes mean a new asset ID. Asset/file access rechecks active assignment after storage reads to handle revocation mid-download. Preview requests with nonready assets show processing/conflict, never broken URLs.

For adoption with artwork, prepare event copies **before** final apply using the preview/adoption intent's dedupe key; reserve EVENT_COPY tombstones, copy sanitized source in a bounded worker outside locks, and mark a materialization receipt ready for this event,targetVersion,sourceHash. Preview responds202/pending if preparation is required and supplies a poll URL `GET /invitations/:slug/template-upgrade-previews/:previewId`; it returns ready preview only when authorized bytes exist. Apply requiring ready receipt stays one atomic database mutation. Stale/abandoned receipts release only unbound event copies and expire in15min; adoption replay returns the original committed result. Lease generation/tombstones prevent a late worker upload resurrecting a retired file. Do not leave a selected pin pointing to an object whose storage put is still pending. No byte copying or per-file remote calls inside publication/adoption transactions.

Cleanup claims max50 eligible unreferenced objects per batch, marks RETIRED under lock only after checking **all** normalized references (draft, immutable version, active preview/materialization/adoption binding and later protected proof) and no live lease, deletes storage outside locks, records deletion, retries failures. Reference creation takes a SHARE row lock on the asset/object so cleanup vs attach has one winning transaction. Tombstones survive to reclaim late uploads; retirement cannot be undone by an expired worker. Organization/event closure inserts cleanup intents and removes eligible transient references in its transaction, never just cascades object metadata away.
