## 1. Shippable result and limits

ADMIN can enter, search, assign and manage enquiries; SUPPORT can create an enquiry assigned to themselves and manage only their currently assigned enquiries. Staff record optional requirements, notes and consultation appointments. Staff may explicitly link customer organization/draft event setup before any quote/payment. The enquiry and its notes remain internal after conversion. No public intake, automatic consultation email/SMS, attachments, lead matching/merging, sales payments, quotes or resource holds are added. Existing account-invitation email remains the sole conversion notification. A phone-only enquiry is valid; creating a new owner invitation later requires an explicitly supplied email. Missing event time remains missing: conversion may link/create just an organization until a real `CreateEventDto` can be supplied.

Independent release: F39 works with the existing `OrganizationMembership.userId @unique`; it neither removes that constraint nor waits for F38, F40, F44, bank certification or fiscal rules. Paid/accepted records are not created or swept. `PILOT_MODE` is unchanged.

## 3. Concrete schema

CUID identifiers, existing UTC timestamp convention (`timestamp(3)` interpreted UTC) for ordinary fields; consultation scheduling fields explicitly `@db.Timestamptz(3)` for reliable range exclusion. Never compare naive consultation timestamps via session timezone. New tables can have required columns from inception because they start empty; new columns on existing tables are nullable first.

* `SalesEnquiry` → `sales_enquiries`: `id`; nullable `organizationId`, nullable `eventId`; `assignedUserId?`; `createdByUserId`; `stage EnquiryStage = NEW` (`NEW/CONTACTED/CONSULTATION/READY_FOR_QUOTE/CLOSED`); `revision Int=1`; optional `eventType EventType`, `approximateLocalDate @db.Date`, `approximateTimezone varchar(64)`, `estimatedGuestCount Int`, `preferredLocale varchar(2)`, `source EnquirySource` (`PHONE/MESSAGING/IN_PERSON/EMAIL/OTHER`); `closedAt?`, `closureReason EnquiryClosureReason?` (`CUSTOMER_DECLINED/UNREACHABLE/DUPLICATE/OTHER`), erasable `closureNote?`; `cleanupDueAt?`; `personalDataClearedAt?`, `clearanceReason?` (`RETENTION/VERIFIED_ERASURE`), `privacyRevision Int=0`; `createdAt/updatedAt`. Source and requirements are optional. No synthetic booking timestamp or arbitrary follow-up field/index.
* `EnquiryContact` → `enquiry_contacts`: `id`, unique `enquiryId`; nullable erasable `name varchar(200)`, normalized `email varchar(200)`, `phone varchar(32)`; `redactedAt?`; `revision Int=1`. Exactly one primary prospect in this slice; no automatic shared customer identity. SQL requires nonblank name and email-or-phone while `redactedAt IS NULL`; redacted contact requires all three fields NULL. Phone input is explicit E.164 (`^\+[1-9][0-9]{6,14}$`), no inferred country; email uses existing normalized-email behavior. Changing identity to a different person is a new enquiry, not overwriting the primary subject.
* `EnquiryContactAddress` → `enquiry_contact_addresses`: `contactId`, `kind EMAIL/PHONE`, `fingerprint` (canonical address fingerprint, no plaintext previous values), `createdAt`; PK `(contactId,kind,fingerprint)`, lookup `(kind,fingerprint,contactId)`. Contact correction appends fingerprints; old raw addresses are not preserved. Purpose is locating this case and its note copies for verified DSAR until PP-D03 clearing. At most 64 distinct address entries per contact; the 65th change requires ADMIN/privacy review and returns a safe contact field conflict, never silently drops traceability. Clearing removes every address-history fingerprint. Equal addresses locate candidates for verified review; they do not merge enquiries or grant tenant access. Identical shared/recycled addresses require human identity review, especially phone numbers. Fingerprints are still restricted personal data; no indefinite historical-identifier store is added.
* `EnquiryNote` → `enquiry_notes`: `id`, `enquiryId`, `kind GENERAL/CONSULTATION`, nullable `consultationId`, nullable erasable `body varchar(10000)`, `createdByUserId`, `createdAt`, `redactedAt?`. Append only except privacy redaction; correction is a new note, not immutable PII copies. Every note belongs to the primary prospect for privacy scope; do not record unrelated people's identifiers. If other people are relevant, staff request manual redaction/export review, not a name-search inference.
* `Consultation` → `consultations`: `id`, `enquiryId`, `operatorUserId` (non-null), `startsAt/endsAt timestamptz(3)`, `timezone varchar(64)`, `status SCHEDULED/COMPLETED/CANCELLED`, `revision Int=1`, `completedAt?`, `cancelledAt?`, `createdByUserId`, `createdAt/updatedAt`. Notes use `EnquiryNote`, not duplicated outcome text. SUPPORT can schedule only themselves; ADMIN any active SUPPORT/ADMIN. Case reassignment does not silently move an appointment to another operator; appointment operator remains booked until an authorized explicit change/cancellation. Previous operator still immediately loses all case/notes access. Their own availability response reveals only occupied intervals, never the transferred case ID/contact. This distinction is implementation behavior that must appear in API help.
* `EnquiryActivity` → `enquiry_activities`: `id`, `enquiryId`, `enquiryRevision`, `actorUserId?`, `kind`, `createdAt`, typed safe `metadata` (stage, assignment IDs, related consultation/note IDs, conversion IDs only). Unique `(enquiryId,enquiryRevision)`; one logical activity per command, even when several child rows change. Never copy names, emails, phones, note body, closure prose or raw command payload here. Related notes/appointments appear joined in detail/history subject to the same current enquiry authorization and redaction, including older records after reassignment.
* `EnquiryCommand` → `enquiry_commands`: `id`, `actorUserId`, `operation`, `idempotencyKey varchar(128)`, nullable `requestFingerprint`, nullable `enquiryId`, `resultId?`, `appliedRevision`, `responseStatus`, `createdAt`, `invalidatedAt?`. Unique `(actorUserId,operation,idempotencyKey)`. Holds only result references, never serialized response/DTO, email token or note. `requestFingerprint` is a versioned HMAC of canonical validated intent using a dedicated rotated secret/key ID; null on privacy invalidation. Retain replay identity until an approved idempotency-retention policy exists; do not pick a duration or delete keys automatically.
* `EnquiryConversion` → `enquiry_conversions`: unique `enquiryId`, `id`, non-null `organizationId`, nullable `eventId`, nullable `ownerInviteId`, `convertedByUserId`, `createdAt`, `updatedAt`. First command may link organization only; one later explicit add-event command fills NULL event once, never overwrites existing linkage. Replays cannot rotate owner invitation. SQL tenant-consistent references as below. No duplicated owner email/name/notes in conversion record.
* `OwnerInviteDelivery` → `owner_invite_deliveries`: `id`, unique `organizationInviteId`, `enquiryId?`, `privacyRevision`, nullable `sourceContactId`, `state PENDING/QUEUED/CANCELLED/NEEDS_REVIEW`, `messageId?`, `createdAt/updatedAt`; only IDs and recovery status. Invitation token is generated and its hash + rendered Message committed together by `enqueueInTransaction`, never stored in a generic JSON intent. Missing message template causes transaction rollback before setup is committed. Queue-disabled delivery does not drop Message; it stays queued behind the operational email gate. No consultation delivery intent exists.
* `EnquiryPrivacyFence` → `enquiry_privacy_fences`: singleton `id='intake'`, revision. SHARE for intake writes and snapshots; UPDATE/exclusive for verified erasure. Its purpose is avoiding a new contact arriving between match and redact.
* `EnquiryErasureTombstone` → `enquiry_erasure_tombstones`: PK `(enquiryId,contactId)`, `privacyRevision`, `createdAt`, `sourceRequestId?`; stable opaque IDs and no contact-address fingerprint. Stops that cleared case/contact, stale command/conversion and restored copies from being refilled. It is not a person-wide ban: a new enquiry in an unrelated customer relationship is allowed. Existing organization-specific D21 ERASED suppressions remain the sending guard for the converted organization; unrelated organizations remain unaffected. No new global suppression or global intake blacklist. For phone-only verified erasure, case-bound Message/invite provenance identifies any derived owner contact; independent owners are unaffected.
* `EnquiryPrivacyRedaction` → `enquiry_privacy_redactions`: `id`, `enquiryId` (stable ID, no cascade), `contactId` (stable ID), `reason`, `privacyRevision`, `redactedAt`, `checkpointSequence?`, `checkpointedAt?`. Facts needed to replay erasure and retention clearing after old-backup restore. No raw data. External protected journal holds these same minimal receipts; no retention duration inferred.
* `DataSubjectRequest`: make `subjectEmail` nullable (existing rows unchanged, public DTO still requires real email), add `subjectSource EMAIL/STAFF_ENQUIRY` nullable→backfill EMAIL→constrain, add nullable `enquirySubjectsVerifiedAt`, `erasureAppliedAt`, `erasureCheckpointId`, `erasureResult Json?`; `DataSubjectRequestEnquirySubject` join `(requestId,contactId)` for manually verified phone-only/ambiguous subjects. Store reviewed contact IDs, not new phone numbers in request free text. Add ADMIN-only staff creation of a request with subjectEmail NULL for a person who has no email; no fabricated response address. Existing public submit remains email-required and non-enumerating. Mark staff list/export nullable subjectEmail as an intentional breaking internal-console contract addition in that commit; existing email-based response shapes and public receipts stay compatible.

Foreign keys: case/contact/note/consultation/activity/commands/conversion use RESTRICT or NO ACTION where deletion could remove privacy/audit/replay facts; no F39 delete API. Assignment/operator User references use RESTRICT and existing soft closure. Historical actor IDs are scalar snapshots like existing invitation invitedByUserId, deliberately without User FK acquisition in command/activity inserts; they never grant authority or cascade deletion of cases. Organization/event links use RESTRICT; clearing a prospect must never delete organization/event. Event deletion remains allowed for unconverted events; a linked event requires staff resolve/detach the internal link through a reviewed future command rather than silently losing conversion facts. Document this deliberate compatibility restriction before release. Customer closure must preserve internal sales references. Do not change unrelated legacy deletion semantics by surprise.

## 4. Permission truth table and immediate revocation

Add `enquiry:manage` and `enquiry:assign` to ALL_PERMISSIONS **and PLATFORM_ONLY in the same change**. SUPPORT receives manage only; ADMIN receives both. Tests enumerate every org/event role and vendor/guest actor to prove neither permission leaks through `CUSTOMER_OWNED = ALL_PERMISSIONS.filter(...)`. Quote prices are not introduced or returned. `concierge:manage` remains an existing broad setup ability; it is insufficient by itself for accessing an enquiry.

| Actor / current case | Create | List/read/contact/history/notes/consultations | Ordinary mutation / close / reopen / convert | Assign |
|---|---|---|---|---|
| Active ADMIN | Yes; explicit null or active staff assignee | All | All | Yes to active SUPPORT/ADMIN or null |
| Active SUPPORT, assigned to actor | Yes, assignee forced actor | Own assigned only | Yes, cannot edit assignee; consultation operator self only | No |
| Active SUPPORT, different assignee or unassigned | Create own only | No; detail/child returns 404 | No, including command replay | No |
| Former assignee after reassignment | Create own only | No, even old appointment/note/command IDs | No | No |
| Customer OWNER/MANAGER/member/event role, including linked organization | No | No | No | No |
| DESIGNER, vendor/guest capability, inactive/deleted staff | No | No | No | No |

List filters `assignedUserId=actor.userId` in SQL before paging/counts, not after fetching. Detail/child/history queries constrain enquiry ID plus current assignment; child ID alone never authorizes. No assigned operator grant in organization/event memberships, no cache of case access, no capability token. Mutations reread active platform role and case assignment inside the transaction; guard is only candidate permission. Missing/unassigned/foreign cases share 404; authenticated customer denied by platform guard with 403. All writes enforce expectedRevision after authorization so conflicts do not disclose inaccessible case state.

For strict commit-time ordering, intake writes lock the enquiry root first, then hold SHARE lock on acting `users` row while checking `isActive/platformRole`; demotion/deactivation updates naturally wait. Assignment transaction holds enquiry row FOR UPDATE then sets assignee and writes revision/activity/command atomically. Case reads use a short transaction with enquiry SHARE then current user SHARE until the response is projected; assignment UPDATE waits for preceding readers. A read ordered after reassignment commit returns no case. Already delivered bytes cannot be recalled; no application cache/worker may deliver an old authorized snapshot after a new authorization decision. In-flight old-assignee mutation waits for root then rechecks assignment and fails; no grants are copied into tokens.

## 6. Canonical idempotency, revisions and lock protocol

Canonicalize only after DTO validation: deterministic field order; normalized email/phone; date-only preserved; timestamps normalized to UTC milliseconds; omitted optional fields distinguished from explicit null on PATCH; create defaults applied; nested arrays absent in intake. Include operation, target enquiry ID, actor ID and expected revision in fingerprint. HMAC version/key ID persisted; config rotation keeps previous verify keys while commands exist. Do not include generated IDs/time. Same actor/operation/key + same intent is one effect; same key + different intent =>409. Receipt insertion uses `INSERT ... ON CONFLICT DO NOTHING` then locked read; transaction rollback removes claim, so retry can perform effect. No PII reply snapshots. Erasure/retention sets affected fingerprints NULL/invalidatedAt and leaves key as a permanently spent command: replay returns safe 409 `SUBJECT_ERASED`/`INTENT_REDACTED`, never treats missing fingerprint as a fresh intent or returns original contact body. Live access is rechecked before any replay projection.

All successful mutations increment `SalesEnquiry.revision` exactly once and create exactly one activity and receipt in that transaction. Child consultation edits also CAS child revision. Read revision never reserves access. Opposing races to prove with two real DB connections and test barriers:

* note/contact/stage vs assignment: root lock winner commits; loser rereads access/revision and cannot edit the new owner's case. Reassignment cannot commit while old operator's authorized read is still projecting under SHARE.
* two overlapping consultations in different enquiries: exclusion lets one commit; loser returns safe 409 and rolls back root activity/revision/receipt. Adjacent `[10:00,11:00)` and `[11:00,12:00)` both succeed. Every shift/operator/time/status update runs the same invariant.
* cancel vs schedule same interval: scheduling waits for conflicting tuple; succeeds after cancellation commit, fails if cancellation rolls back. No overlap gap between a read and write.
* consultation update vs case reassignment: root serializes; transfer never grants old operator history even if their appointment remains scheduled.
* close/reopen vs retention: root lock and rechecked latest deadline/stage determine winner. Reopen first prevents purge; purge first clears PII, and later reopen returns redaction marker without revival.
* erasure vs create/edit/convert/invite accept/message enqueue: shared/exclusive fence gives either full write followed by erase, or erase followed by rejection of that cleared case/contact or stale source revision. An unrelated new enquiry remains allowed; no address-wide ban is inferred. No stale contact copied after erasure. No activity/note copy escapes.
* simultaneous conversion/replay/new keys: unique enquiry conversion plus root lock returns one setup and one owner invitation. Conversion of two different enquiries to the same new owner additionally uses owner lock plus pending OWNER invitation lookup, so it cannot create two pending owner organizations.
* conversion vs self-created organization/invite acceptance: all take owner lock; re-resolve 0/1/many membership plus pending organization inside lock.
