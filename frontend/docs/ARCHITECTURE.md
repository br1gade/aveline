Rules:

- **A link preview never names a guest.** It is built from the event and `coverUrl`.
- **Invitations are always `noindex`.**
- **Time-dependent UI renders after hydration** (the countdown).
- **A form that submits from JavaScript** has `method="post"` and a submit button disabled until
  hydration (`useIsHydrated`), so nothing typed, a password above all, can reach the address bar
  before React runs. The account forms, the event forms, the guest list's dialogs, the import
  form, the venue form, the guest reply form and the seating dialogs do (design PD-41).
- **No browser globals at module scope.**
- **Filters live in the address,** written in place (`replace`) and without a scroll jump, so a
  reload or a shared link keeps them. The guest list's search box holds its own text and the
  address catches up 300 ms after typing stops; a change of address it did not write itself
  (Back, a link) replaces what is in the box.

## 3. The route contract

The backend builds links to client paths from `PUBLIC_APP_URL` (default `http://localhost:5173`).
They are defined once in `ROUTE_PATHS` (`src/route-paths.ts`), used by `src/routes.ts`, and pinned
by a test against both the backend's sources and the table `docs/API.md` §3 publishes (FR-8),
each way. Renaming one is a breaking change for the backend's emails. They include
the bank's default return pages, `/tickets/return` and `/billing/return`, and since 31 October
2026 a public event's `/events/:slug`, which the backend builds as its `metadata.canonicalPath`,
and since 10 November the data-request form, `/privacy-request`, which every new invitation email
links (FR-136);
React Router ranks the static `/tickets/return` above `/tickets/:accessToken`. The client's own paths, which nothing
outside links to, are in `APP_PATHS` beside them: registering, the app's home, onboarding, the
event pages, an event's guest list and import, its venues (adding and correcting one) and its
invitation's publishing and sending, how guests answer, the designer, guests' photos, the
agreements and the seating, the exports, ticket sales (`/app/events/:eventId/tickets`, its types
and announcement), the orders and an event's activity, the organization's own settings
(`/app/organization`, beside the chooser at `/app/organizations`), Aveline's own staff's tools
(`/app/staff`, its customers, data requests and access reviews); the public price list,
`/pricing`; the Help page, `/help`; checkout, `/events/:slug/checkout`, and the buyer's order once
its token is out of the address, `/tickets`. The static `/app/events/new` ranks above
`/app/events/:eventId`; `/venues/new` would rank above a `/venues/:venueId`, and `/guests/import`
above a `/guests/:guestId`.

## 4. The API layer (`src/api/`)

- `npm run api:generate` writes `src/api/schema.ts` (gitignored) from `../backend/openapi.json`,
  with `--default-non-nullable false`: a request field the server defaults stays optional, as the
  API reads it. The same script writes `src/api/public-paths.ts` (gitignored too): the operations
  the spec declares `security: []` (FR-2).
- **Two clients:** `publicApi` without credentials (guest pages), `appApi` with the bearer token
  and refresh. The public one is typed over the public operations alone, and the signed-in one
  carries a type-only brand, so a function a public page calls must take `PublicApiClient` and can
  then call nothing that needs a session (FR-2). Either client can be given to such a function.
- **One `fetch` underneath both:**
  - it sends its own `x-request-id`, so a reference exists even when no answer arrives;
  - on 401 it refreshes once and retries; on 403 it never retries;
  - it asks for errors in the page's language (`accept-language`): the browser session reads
    `<html lang>` at each call, the guest reply the invitation's language;
  - every failure becomes one `ApiError { status, messages, fieldErrors, requestId, path }`, with
    the backend's `code`, `action`, `userMessage` and `details` beside them since `eb77cd4`. The
    pages keep their own words: `userMessage` is generic per status. `code` tells an attendance
    change (`ATTENDANCE_CHANGED`) from other conflicts. Since `34ac1e6` the organization, template
    and enquiry routes have codes of their own; no route whose refusals the client recognises by
    their words has one yet (FR-28).
- `retryOnConflict` (`src/api/retry.ts`) tries a read once more after a 409; the guest page's read
  uses it for "Invitation changed while loading", which docs/API.md §6 says to retry.
- `loaded` (`src/api/loaded.ts`) turns a part of a page that loads on its own into `Loaded<T>`:
  ready, refused to this role (403), or failed with its problem, so the rest of the page stands.
  The invitation page and the designer use it.
- `createRetryKey` (`src/api/retry-key.ts`) keeps a queued start's client UUID for the next press
  with the same choices after no answer or a server failure, either of which may have queued it;
  any other answer ends it. Automatic seating and exports use it.
- `expectFile` (`src/api/file.ts`) is `expectData` for a call made with `parseAs: 'blob'`: the
  bytes, their type, and the name `Content-Disposition` gives, exposed cross-origin (FR-10). Exports
  use it.
- **Base URL:** in the browser, the same origin; the Vite proxy sends `/api`, and `/files` (the
  backend's own-disk uploads when no S3 is configured), to `API_INTERNAL_URL` (default
  `http://localhost:3000`) in development. On the server,
  `API_INTERNAL_URL` directly. Production is not agreed (FR-11): the backend's production template
  puts the API on its own origin, which would make every browser call cross-origin.
- **Response types come from the schema** (FR-1): `expectData(call)` with no type gives the body the
  operation declares, and `ResponseOf<'Controller_methodResponse'>` names one. A feature may keep
  its own wire types, written from the guide; the call checks them, as the declared body must fit
  them, so a field the schema retypes fails the typecheck. Its `read.ts` keeps only the fields a page
  uses and maps a value the client doesn't know. `expectData` takes no type from where the call
  stands (`NoInfer`), so a `return` or an argument is checked too. A type is passed,
  `expectData<T>(call)`, only where the schema is looser than `docs/API.md`: the guest page's two
  reads, the guest's reply, the designer's three previews and the vendor's brief (FR-149).
- **What the caller may do** (FR-6, design PD-190): `features/permissions` reads it once per event
  (`routes/app/event-access.tsx`) and on entering the organization's own pages
  (`organization-access.tsx`), and again when a page reads itself after a write, or on leaving the
  organization's page; `useCan` and `Permitted` answer from the nearest. Unknown means everything is
  offered, as before. `Permitted` hides one action; `ChangeableWith` shows a page a role may read
  but not change with its controls off, under one line (design PD-193).

## 5. Session (`src/api/session/`)

The access token in memory, the refresh token in `localStorage` behind `tokenStore` (A3), so
moving it to an httpOnly cookie (FR-12) changes one module. Refresh is single-flight within a tab
and across tabs through a Web Lock; logout broadcasts on a `BroadcastChannel`.

`browser-session.ts` wires these to the API, as one lazy instance in the browser:

- **`start`** after a login keeps the pair and refreshes a minute before the access token expires.
- **`ensureSignedIn`** before a signed-in page: a reload has no access token in memory, so it
  refreshes from the stored refresh token first. A page's `clientLoader` calls it through
  `requireSignedIn`, which otherwise redirects to `/sign-in?next=…`; `safeNext` follows `next`
  only to a path under `/app`.
- **Ending:** a refused refresh, signing out here, or a sign-out in another tab ends the session
  in every tab, and the app goes to sign in. "Sign out on every device" asks first, and keeps the
  session if the server could not be told.
- **After signing in,** the `/app` home creates the organization first when the account has
  neither one nor an event, read from `GET /me/organizations` and `GET /events` (FR-5).

What the backend does since 23 October 2026 (`docs/API.md` §2, `docs/ACCESS_CONTROL.md` §5):

- **Register does not sign in.** It answers `202` whether or not the address has an account, so
  the client logs in next.
- **A refresh token presented more than a minute after it was replaced is treated as theft:**
  every session the account has ends. Within the minute it is only refused, as is one a password
  reset or "sign out everywhere" ended. The cross-tab lock, which re-reads the
  stored token, is what keeps a second tab from presenting a stale one. Where Web Locks are
  missing, a refused token may have lost a race: if the store holds a newer one, it is tried
  once, and the store is cleared only if it still holds the refused token. A network failure
  never clears it.
- **A password reset or "sign out everywhere" ends sessions at once:** access tokens already
  issued answer `401`, and the refresh that follows is refused.

## 6. Language, time and money

- **Guest pages use the response's `locale`** for `<html lang>`, the interface strings and the
  content. No locale path prefix.
- **Account and app pages negotiate** (design PD-40): `?lang=` from the switcher, remembered in an
  `aveline-lang` cookie, then `Accept-Language`, then English (`src/lib/i18n/negotiate.ts`). The
  switcher is shared (`src/ui/language-switcher.tsx`); on these pages it navigates client-side, so
  a reset or invitation page keeps the token it holds in memory.
- **Interface strings** live in `src/locales/<hy|ru|en|fr>/<namespace>.json`. English is the
  source; Armenian and Russian are drafts until a native reader checks them (design PD-9). French
  is translated from English and ships without a native reading (design C-23). A test checks that every language has the same keys and the plural forms it needs, and
  that French spaces before `; : ! ?` and inside « » are unbreakable (U+202F, or U+00A0 before a
  colon).
- **Plurals** use `Intl.PluralRules`, which covers Russian's four categories and French's three
  (`one` takes 0 and 1; `many` takes round millions and is worded as `other`). Counts in sentences
  ("2,000 guests") go through i18next's `number` format, on `Intl.NumberFormat`; the app pages
  that use it render in the browser only, so the server's ICU never formats them.
- **Time** (`src/lib/time`) formats in `event.timezone`. English, Russian and French (`fr-FR`)
  dates use `Intl.DateTimeFormat`; Node's and Chrome's French data agree. **Armenian dates are composed by hand** in the design's form
  ("շաբաթ, 12 հունիսի 2027 թ.") and **times are built from numeric parts** in every language,
  because the server's and the browser's ICU disagree: Chrome ships no Armenian date data and
  falls back to US English. Anything the two runtimes format differently breaks hydration.
- **Typed times** (`src/lib/time/zoned-input.ts`): a host types a date and a time in the event's
  zone, in the browser's own inputs. `instantFromWallTime` finds the instant from the zone's
  offsets through `Intl`, never the device's zone. A time the clocks skip is refused on the time
  field, and one they repeat is the earlier (design PD-43). The zones offered are the browser's
  `Intl.supportedValuesOf('timeZone')` plus the event's own, since browsers name some zones
  differently and an edit must not change one silently.
- **Money** (`src/lib/money`) works on minor-unit strings; `parseFloat` fails lint. **Armenian
  amounts are composed by hand** ("15 000 ֏"), for the reason Armenian dates are: Chrome has no
  Armenian number data and says "AMD 15,000" where Node says "15 000 ֏". The hand-made form matches
  Node's, and a test fails if `Intl.NumberFormat` is asked for Armenian.

## 7. The invitation renderer (`src/features/invitation-renderer/`)

Pure, safe to render on the server, light on JavaScript. Specified by
[design/GUEST_INVITATION.md](design/GUEST_INVITATION.md) and
[design/DESIGN_SYSTEM.md](design/DESIGN_SYSTEM.md).

- **Shape:** `types.ts` (the interim payload types), `schemas.ts` (lenient Zod readers for each
  block's free JSON: a malformed field is dropped, never an error), `theme.ts`, `blocks/` with
  `registry.ts`, `components/`, and `invitation-page.tsx`, which lays out the cover, the personal
  card, the letter, the footer and the reply bar.
- **Blocks:** a registry keyed by block type. The array order is kept; an unknown type renders
  nothing; a `null` or unknown variant falls back to the default.
- **Two public surfaces:** `index.ts` for components, and `index.server.ts` for the server-only
  loader, so the internal API address never reaches the browser bundle. The boundary lint allows
  exactly these two.
- **Theme:** the payload names a palette but carries no colours (BQ-1). A temporary stand-in
  (design PD-21) maps the name to roles and knows only "bordeaux"; anything else falls back. It is
  deleted when the backend sends colours.
- **Two more slots,** on personal links only: `renderPersonal` inside the personal card, under the
  names (correcting one's name, `features/guest-name`), and `renderContributions`, a section after
  the letter (the guests' photos, `features/gallery`). The preview passes neither.
- **The reply form** is a separate feature (`src/features/guest-reply/`) that the guest page puts
  into the RSVP block's slot through `renderReply`, so the renderer stays usable for a designer
  preview later. The route holds the saved reply and passes its summary (status, head count,
  household names) and, once sent, the "Thank you" heading back into the page.
- **What each block reads** is one table, `blocks/fields.ts` (`BLOCK_EDITING`): its content fields,
  NOTES' items, DRESS_CODE's swatches, which media it shows, and which facts come from the event.
  The host's designer builds its forms from it, so the editor and the renderer agree on the names
  (design R-30, FR-43); `fields.test.tsx` renders every listed field.
- **A preview** (`isPreview`, in the backend's template previews) renders as a generic page whose
  reply section says guests answer on their own link and a preview collects nothing (design PD-59).
  The designer puts it in an i18n instance of the preview's own language, so the renderer's words
  are the guests'.
- **The reply follows the invitation's `rsvpFields`:** a built-in question shows only when it is
  switched on, since sending a switched-off one is refused, and dietary and drink offer the host's
  own choices. Every attending member and added guest answers the host's questions for
  themselves (PD-38). `payload.ts` sends only what changed, and the page's language when it is
  not the one stored for the guest, so their confirmation and reminders follow what they read.
- **Provisional defaults** from `DESIGN_DECISIONS.md` §6 are followed in code, and named in a
  comment where the code departs from the canvas.

## 8. Styling, tokens and fonts

- `src/styles/tokens.json` is a copy of the design system's `tokens.json`.
  `npm run tokens` generates `src/styles/tokens.css` (CSS variables for the Ivory and Bordeaux
  themes) and `src/styles/theme.css` (the Tailwind `@theme` mapping and one `type-*` utility per
  type style). `npm run tokens:check` fails on drift. **The generated CSS is the source of truth
  for code**; the JSON is its input.
- **Type sizes are fluid** between 360 and 1440 px (`clamp()` in rem). `tokens.json` holds the
  desktop sizes only in each style's usage note ("40/46px on desktop"); the generator reads them
  with a strict pattern and fails the build if a note mentions desktop in other words. The
  Armenian adjustments (tracking, body line height) are in `src/styles/app.css`.
- **Components** use semantic tokens through Tailwind classes. Shared, presentational ones live
  in `src/ui/` (buttons, links, notices, form controls in `src/ui/form/`); the invitation's own in
  the renderer. The account and app forms' pieces are in `src/ui/app-form/`: `AppForm`, which
  posts (PD-41), `SubmitButton`, `TextInputField`, `SelectField` and `ProblemAlert`, with
  `problemFrom` in `src/api/problems.ts`; and `LeaveGuard`, around the app in its layout, which a
  page form joins with `useLeaveGuard(form)` to ask before unsaved changes are left
  (PD-119).
- **The app's kit** is shadcn/ui (C-14) in `src/ui/kit/`, added with the CLI from
  `components.json` and then owned by us: it passes our lint and imports our `cn` (`src/ui/cn.ts`,
  clsx with tailwind-merge). The native select, checkbox and textarea were written by hand in the
  same form, since the CLI would add `lucide-react`, and so was the dialog, which has no close icon:
  Cancel and Escape close it. The kit never imports it: the radio's dot is
  drawn in CSS, and the select's chevron and the checkbox's check come from `src/ui/icon.tsx`.
  `src/styles/app-kit.css` maps its variables onto the tokens exactly as DESIGN_SYSTEM §12
  tabulates; the CLI's own palette is not used. Its `dark:` classes stay off until a dark mode is
  designed, and its corners are square (PD-39). The invitation does not use the kit.
- **Icons** are Lucide path data copied into `src/ui/icon.tsx` with Lucide's ISC notice, rather
  than the `lucide-react` dependency, for the dozen the guest page uses.
- **Fonts:** the four Noto families as variable WOFF2, self-hosted through `@fontsource-variable`
  packages, each split into script subsets by `unicode-range`, so a page downloads only the scripts
  it uses. The stacks follow `tokens.json`: the Armenian family first, then base Noto. The Armenian
  families carry a Latin in the same design (DESIGN_SYSTEM §3.1), so Armenian, Latin and digits
  come from them, French accents, « », `’` and the narrow no-break space included (their `latin`
  and `latin-ext` subsets); Cyrillic, `№` and `₽` fall through to base Noto. A test
  (`src/styles/fonts.test.ts`) checks that both stacks' subsets cover every interface string.
  `font-synthesis: none`. **The guest pages preload two files,** the serif and the sans in the page's
  script, with React's `preload` from `features/invitation-renderer/fonts.ts`, at the address the
  stylesheet names, so it is one download; the rest load as needed.
- **Strings** load by who needs them: `src/locales/guest.ts` is always there (`common`, `invitation`,
  `reply`, `gallery`, `guest-agreements`), and `public.ts` and `app.ts` are imported by their routes
  alone, adding to the one object every i18next instance reads (`registry.ts`). Before this the guest
  page carried every feature's words in four languages: 187 KB of its 451 KB gzipped JavaScript.
  `locales/index.ts` still holds them all, for the types and the parity tests, and nothing at run time
  imports it. A new namespace goes in the file of who needs it.
- **Budgets:** `npm run check:budgets`, in `verify`, sums the gzipped JavaScript and CSS a guest route
  loads first, from the build's own route manifest. A personal page is at most 300 KB of JavaScript
  and a generic one 205 KB, measured on 4 November 2026 with a small margin. The largest pieces left are
  the router and React (`entry.client`), and on a personal page `features/gallery`'s hosts' side, which
  `events` comes with through its one `index.ts`. Raising a limit means saying why here.
- **The invitation keeps its palette** whatever the device's dark mode (`color-scheme: light`).

## 9. Errors, headers and observability

- **Errors by status:** 400 maps to fields and the form; 401 refreshes once; 403 never retries;
  404 shows the not-found page; 409, 413 and 429 are handled where they happen; 5xx and network
  errors show the route's error state with the request id as a reference. On the guest list a 404
  or a conflict on a write reloads the list behind the message, since it is out of date.
- **An event the account cannot see answers 403, not 404** (`docs/BACKLOG.md` §4), so the event
  pages say "not available" for both. An action the access read doesn't grant is not offered
  (FR-6, PD-190), on the pages moved so far; every 403 is still explained when it happens.
- **Headers** (`src/entry.server.tsx`, `src/lib/security`): a nonce-based Content Security Policy
  in production, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, but for the designer's
  draft preview (`/app/events/:eventId/design/draft-preview`), which the app frames itself:
  `frame-ancestors 'self'` and `SAMEORIGIN` there alone (PD-153). Every response for a
  path that carries a capability token (a personal invitation today), or a `?token=` query (the
  reset, email and invitation pages; `carriesCapability`), gets
  `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store` and
  `X-Robots-Tag: noindex, nofollow`, applied by address in `entry.server.tsx`, so error pages and
  `.data` requests have them too. The generic link may be kept by the guest's browser for a
  minute (`private, max-age=60`), with the same referrer and robots rules. Never by a shared
  cache: every page carries its own script nonce.
- **Token links:** a page opened from `?token=` reads it once, keeps it in memory and takes it out
  of the address bar straight after hydration. It never goes into a link on the page, so the
  server's HTML does not hold it.
- **The buyer's order token** (since 31 October 2026, design PD-81) is the one token a tab keeps
  beyond memory: the bank's return to `/tickets/return` carries none, and docs/API.md §5 asks the
  client to store it. `features/ticket-order/token-store.ts` holds it under one `sessionStorage` key (this tab only), in memory where
  storage is refused. The emailed `/tickets/:accessToken` renders a shell that never reads it;
  after hydration the tab holds it and the address becomes `/tickets`, which `entry.server.tsx`
  protects by its exact path, as the capability paths are. The token goes only to the API's
  `/ticket-orders/…`; tests plant one and check the page, the console and the address. A ticket's
  code, which admits at the door, is shown on that page, and to roles with contact access on the
  orders page and the ticket manifest, and is never logged. At the door it stays in one field, never
  in the address or storage (design PD-91). The bank's query on
  the return is taken out of the address too, since it may carry the payment's order number.
- **A vendor's brief token** (since 4 November 2026, design PD-124) is held like the buyer's order,
  but **in memory only**: nothing comes back to the page without its link, so no storage, cookie
  or history state holds it. `/briefs/:briefToken` renders a frame that never reads it; after
  hydration `features/vendor-brief/token-holder.ts` holds it and the address becomes `/briefs`,
  which `entry.server.tsx` protects by its exact path beside `/tickets`. A reload holds nothing and
  asks for the link again; "Try again" reads again with the token held. The token goes only to the
  API's `/briefs/…`. On the host's side it arrives in `GET /events/:id/vendors` for a role with
  `vendor:write`; `features/vendors/read.ts` names every field it keeps, and the booking page never
  renders it, only hands `/briefs/<token>` on the client's public origin (`VITE_PUBLIC_ORIGIN`) to
  the clipboard when Copy is pressed. Tests plant a token made at run time and check the page,
  storage, the console and the address; a production build was checked the same way, with the
  headers, the server's HTML and every request's address and referrer (4 November 2026, against a
  mock). The development server's inline styles send the document's address as the referrer of
  font requests; the production build's stylesheet does not.
- **Not found:** a guest link that opens nothing (wrong, a draft, past its retention date) is a
  404 with the invitation's own not-found page, in all four languages.
- **A guest's token** (their personal link segment) arrives in `GET /events/:eventId/guests` and
  in the answers to adding and correcting a guest (FR-29). It stops where the response arrives:
  `features/guests/read.ts` builds every object by naming its fields, and the write calls resolve
  to nothing. It is never rendered, stored, logged or put in an address, and no test fixture holds
  one: the tests make theirs at run time and check it went nowhere. The venue, publishing,
  sending and delivery answers carry none (checked against the backend's services on 25 October
  2026); their readers (`features/venues/read.ts`, `features/sending/read.ts`) still name every
  field they keep, and the tests put a token into the venue, draft, send and delivery answers and
  check it went nowhere. Publishing, closing and reopening keep only the answer's `status`.
- **Private files** (guests' photos, drawn signatures) are read through the API client and shown
  from an object URL (`src/ui/private-image.tsx`, `src/api/private-file.ts`), never from an
  `<img src>`: a guest's file address carries their token, which must not reach the page or every
  resource listing, and a host's needs the bearer token, which an image element cannot send. The
  page holds only `blob:` addresses; the request goes where every guest call already goes, the
  guest's own link, with `Referrer-Policy: no-referrer` on the page and on the file. A picture is
  read only near the screen, four at a time across the page, a 429 tried again after 2 and 4
  seconds (docs/API.md §11), and its URL is released when it leaves the page. No log names a
  request address; an `ApiError`'s `path` comes back from the backend with the token replaced. The
  agreements page names guests from the guest list, read through `features/guests`' own reader,
  so no token goes further there either (FR-49). The seating answers carry no token (checked
  against `seating.service.ts`, `seating-jobs.service.ts` and `localized-seating.ts` on 30 October
  2026); the seating page reads the guest list through the same reader, for who is coming and to
  name the households a run could not seat (FR-55), and its tests put a token into that list and
  check it went nowhere. A guest's own table comes in their personal page's `guest.seating`, which
  holds their own household only. The orders page offers guests to link and names linked guests
  through the same reader, and the ticketing readers (`ticket-sales/read.ts`,
  `ticket-orders/read.ts`) name the fields they keep, so a token the backend added would go no
  further.
- **Exports** (`features/exports`) are read through the API client with the bearer token, as a blob
  (`src/api/file.ts`, `expectFile`), and handed to the browser from an object URL released half a
  minute later (`src/ui/save-file.ts`). The page never links to a file and keeps no download
  address: the readers drop `downloadPath`, and the client builds the call. The name comes from
  `Content-Disposition`, exposed cross-origin (FR-10), or from the backend's own pattern when a
  response comes without one; an answer of another type than the format asked for is refused, not saved.
  The export answers carry no guest token (checked against `export-snapshots.service.ts` and
  `exports.service.ts` at `eb77cd4`); their readers still name every field they keep, and the
  tests plant a token in the answers and check it went nowhere. A file's contents are never read,
  logged or kept by the page.
- **Private artwork** (design PD-140, since 4 November 2026) is an authored template's. Its address is
  relative to the API and, on a personal page, holds the guest's token, so
  `features/invitation-renderer/private-artwork.ts` rewrites it to the asset's id in the server's
  reader, before the loader's data or the HTML can hold it (FR-115). Any other string holding
  `/design-assets/` is removed, with no id, so a shape it doesn't know loses a picture, not the token.
  A private cover gives no link preview. The picture is read through the API, by the guest's link, the generic one or the host's
  session, and shown as `src/ui/private-image.tsx` shows the others. Tests plant a token at run time
  and check the payload, the server's HTML and the page; a production build was checked the same way.
- **The bank's return for a plan** is protected as a capability page, as its query may name the
  payment's order number (`/tickets/return` already was, by its path). It stores nothing: confirm is
  asked of the newest invoice (PD-130), and the order number stops at `features/billing/read.ts`.
- **The data-request form** (`/privacy-request`, design PD-156) holds what someone types about a person,
  so like checkout its page is `no-store`, with no copy for the Back button of a shared computer. The
  address and notes go in a POST and leave the page when sent; a production build was checked for them
  in addresses, referrers, storage and the page. **An event's activity** names people and is an
  owner's; only the fields a row shows reach the page, and no route it shows can hold a token, as the
  trail records patterns. **Organization invitations:** the answer's development link holds a token, and
  the reader keeps only the address and role.
- **The production server** (`server/`) logs one line per request: the method (one it doesn't know
  is `OTHER`), the path through `redactUrl` with its query dropped whole, the status and the time. The
  path is first decoded until it stops changing (at most four times, then `[unreadable]`), its `.`,
  `..`, backslashes and repeated slashes resolved, and lower-cased, as the router matches `/Tickets/…`
  and a client may write a token in shapes the patterns don't know. An address that can't be decoded,
  or a `Host` no address can be made from, ends in a 400 before the router, which would warn with the
  URL. Errors go through `redactText`, which ignores case and takes out `token=` and `orderId=`, and
  `handleError` in `entry.server.tsx` replaces React Router's own logging, which would print a loader's
  error whole. It refuses to start without `API_INTERNAL_URL`, whose development default would, in
  production, be itself. No compression or TLS: the proxy's (FR-11). `/healthz` isn't logged.
- **Addresses in the invitation's answers:** the delivery report omits `toAddress` without
  `guest:contact:read`, and the client reads a missing one as "not yours to see". Its
  `failureReason` is the mail server's own reply, which often quotes the address, so the backend
  withholds it from such a role (FR-35), and it is shown only when the address arrived too. The send answer carries `toAddress` whatever the role
  (FR-34); it is shown where it arrived and never logged. A Telegram address is a chat number and
  is never shown, only "on Telegram".
- **Publishing's refusals** are English sentences without a code (FR-32). The three the backend
  has are recognised by their exact text and worded in the page's language, each linked to its fix
  (design PD-49); anything else is shown as it came, marked `lang="en"`. A send's unreachable
  reasons are shown in English the same way (FR-33).
- **Capability links** are redacted with the patterns of `backend/src/common/redact-url.ts`
  before anything is logged, and a test reads that file so the copy cannot drift. A payment's
  order number and an invitee's address are redacted too, though they make no page a capability
  page. Free text also loses any `token=` query value, which the client's own reset and
  invitation links carry.
- **Sentry and analytics:** none yet.
