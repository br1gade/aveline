> and §5 ([FRONTEND_SETUP_PROPOSAL.md](FRONTEND_SETUP_PROPOSAL.md)). The proposal is deleted once
> this file and [WORKFLOW.md](WORKFLOW.md) hold its decisions (A11). Where they differ, this file

> The first surface is the guest invitation. The organizer app comes later (design decision C-7);
> since 23 October 2026 its way in exists: the account pages and the app's first screens, then
> creating an event, opening it and correcting its details.

## 1. Stack

| Concern | Choice |
|---|---|
| Language | TypeScript 6.0, strict (`typescript-eslint` 8.71 supports `<6.1`) |
| UI and framework | React 19 with **React Router 8 in framework mode**, server rendering from day one (A1), on Vite 8 |
| Routing | `src/routes.ts`, config-based, so the route contract sits in one file |
| API client | `openapi-fetch` over types generated by `openapi-typescript` from `backend/openapi.json` |
| Forms | React Hook Form with Zod 4 |
| Styling | Tailwind CSS 4, with tokens generated from the design system's `tokens.json` |
| App UI kit | shadcn/ui on Radix (C-14), in `src/ui/kit/`, mapped onto the tokens (§8) |
| Languages | i18next with react-i18next (A2): hy, ru, en |
| Time | `Intl` in the event's time zone (`src/lib/time`), both ways: what is shown, and what a host types; no date library |
| Money | Our own `src/lib/money`, on strings and `BigInt` |
| Tests | Vitest 5 with Testing Library and MSW; Playwright against the real local backend; axe |
| Lint and format | ESLint 10 with type-checked `typescript-eslint`, react-hooks, jsx-a11y (the ESLint 10 fork); Prettier with the backend's settings |
| Node | 24 (`frontend/.nvmrc`); see the decision log |

## 2. Rendering

| Route group | Rendering | Data |
|---|---|---|
| Public: `/invitations/:slug`, `/invitations/:slug/g/:guestToken` | Server | A server `loader` against the public API; `meta` from the response |
| Capability, later: `/tickets/:accessToken`, `/briefs/:briefToken` | Server shell | Fetched in the browser; `noindex`; `no-referrer` |
| Account: `/sign-in`, `/register`, `/reset-password`, `/verify-email`, `/accept-invite`, `/accept-event-invite` | Server, the form included | A server `loader` for the language only; forms submit from the browser. Sign-in and register skip to the app when a session is stored (`clientLoader`) |
| App: `/app`, `/app/welcome`, `/app/events/new`, `/app/events/:eventId`, `/app/events/:eventId/edit` | The server renders the loading state, in the negotiated language | The `/app` segment's `loader` gives the language; a pathless layout under it checks the session in its `clientLoader`; each page's `clientLoader` reads the API. The event pages' `ErrorBoundary` shows an event that cannot be opened inside the app's frame |

Rules:

- **A link preview never names a guest.** It is built from the event and `coverUrl`.
- **Invitations are always `noindex`.**
- **Time-dependent UI renders after hydration** (the countdown).
- **A form that submits from JavaScript** has `method="post"` and a submit button disabled until
  hydration (`useIsHydrated`), so nothing typed, a password above all, can reach the address bar
  before React runs. The account forms, the event forms and the guest reply form do (design
  PD-41).
- **No browser globals at module scope.**

## 3. The route contract

The backend builds links to client paths from `PUBLIC_APP_URL` (default `http://localhost:5173`).
They are defined once in `ROUTE_PATHS` (`src/route-paths.ts`), used by `src/routes.ts`, and pinned
by a test that reads the backend's sources. Renaming one is a
breaking change for the backend's emails (FR-8 asks for the table in `docs/API.md`). They include
the bank's default return pages, `/tickets/return` and `/billing/return`; React Router ranks the
static `/tickets/return` above `/tickets/:accessToken`. The client's own paths, which nothing
outside links to, are in `APP_PATHS` beside them: registering, the app's home, onboarding and the
event pages. The static `/app/events/new` ranks above `/app/events/:eventId`.

## 4. The API layer (`src/api/`)

- `npm run api:generate` writes `src/api/schema.ts` (gitignored) from `../backend/openapi.json`,
  with `--default-non-nullable false`: a request field the server defaults stays optional, as the
  API reads it. The schema declares no responses yet (FR-1); revisit the flag when it does.
- **Two clients:** `publicApi` without credentials (guest pages), `appApi` with the bearer token
  and refresh (later screens).
- **One `fetch` underneath both:**
  - it sends its own `x-request-id`, so a reference exists even cross-origin (FR-10);
  - on 401 it refreshes once and retries; on 403 it never retries;
  - every failure becomes one `ApiError { status, messages, fieldErrors, requestId, path }`.
- **Base URL:** in the browser, the same origin; the Vite proxy sends `/api`, and `/files` (the
  backend's own-disk uploads when no S3 is configured), to `API_INTERNAL_URL` (default
  `http://localhost:3000`) in development. On the server,
  `API_INTERNAL_URL` directly. Production is not agreed (FR-11): the backend's production template
  puts the API on its own origin, which would make every browser call cross-origin.
- **Response types are interim and hand-written** per feature (`types.ts`) until FR-1.

## 5. Session (`src/api/session/`)

The access token in memory, the refresh token in `localStorage` behind `tokenStore` (A3), so
moving it to an httpOnly cookie (FR-12) changes one module. Refresh is single-flight within a tab
and across tabs through a Web Lock; logout broadcasts on a `BroadcastChannel`.

`browser-session.ts` wires these to the API, as one lazy instance in the browser:

- **`start`** after a login keeps the pair and refreshes a minute before the access token expires.
- **`ensureSignedIn`** before a signed-in page: a reload has no access token in memory, so it
  refreshes from the stored refresh token first. A page's `clientLoader` calls it through
  `requireSignedIn`, which otherwise redirects to `/sign-in?next=…`; `safeNext` follows `next`
  only to a path under `/app`.
- **Ending:** a refused refresh, signing out here, or a sign-out in another tab ends the session
  in every tab, and the app goes to sign in. "Sign out on every device" asks first, and keeps the
  session if the server could not be told.
- **FR-3:** the schema declares a `user-agent` header on login and refresh that a browser cannot
  set; one cast in `auth-calls.ts` sends none.
- **After signing in,** the `/app` home creates the organization first when the account has
  neither one nor an event (FR-5 interim, in BACKEND_REQUESTS).

What the backend does since 23 October 2026 (`docs/API.md` §2, `docs/ACCESS_CONTROL.md` §5):

- **Register does not sign in.** It answers `202` whether or not the address has an account, so
  the client logs in next.
- **A refresh token presented more than a minute after it was revoked is treated as theft:**
  every session the account has ends. Within the minute it is only refused. ACCESS_CONTROL §5
  says this of a *replaced* token; the code applies it to any revoked one, including those a
  password reset or "sign out everywhere" revoked (FR-22). The cross-tab lock, which re-reads the
  stored token, is what keeps a second tab from presenting a stale one. Where Web Locks are
  missing, a refused token may have lost a race: if the store holds a newer one, it is tried
  once, and the store is cleared only if it still holds the refused token. A network failure
  never clears it.
- **A password reset or "sign out everywhere" ends sessions at once:** access tokens already
  issued answer `401`, and the refresh that follows is refused.

## 6. Language, time and money

- **Guest pages use the response's `locale`** for `<html lang>`, the interface strings and the
  content. No locale path prefix.
- **Account and app pages negotiate** (design PD-40): `?lang=` from the switcher, remembered in an
  `aveline-lang` cookie, then `Accept-Language`, then English (`src/lib/i18n/negotiate.ts`). The
  switcher is shared (`src/ui/language-switcher.tsx`); on these pages it navigates client-side, so
  a reset or invitation page keeps the token it holds in memory.
- **Interface strings** live in `src/locales/<hy|ru|en>/<namespace>.json`. English is the source;
  Armenian and Russian are drafts until a native reader checks them (design PD-9). A test checks
  that every language has the same keys.
- **Plurals** use `Intl.PluralRules`, which covers Russian's four categories.
- **Time** (`src/lib/time`) formats in `event.timezone`. English and Russian dates use
  `Intl.DateTimeFormat`. **Armenian dates are composed by hand** in the design's form
  ("շաբաթ, 12 հունիսի 2027 թ.") and **times are built from numeric parts** in every language,
  because the server's and the browser's ICU disagree: Chrome ships no Armenian date data and
  falls back to US English. Anything the two runtimes format differently breaks hydration.
- **Typed times** (`src/lib/time/zoned-input.ts`): a host types a date and a time in the event's
  zone, in the browser's own inputs. `instantFromWallTime` finds the instant from the zone's
  offsets through `Intl`, never the device's zone. A time the clocks skip is refused on the time
  field, and one they repeat is the earlier (design PD-43). The zones offered are the browser's
  `Intl.supportedValuesOf('timeZone')` plus the event's own, since browsers name some zones
  differently and an edit must not change one silently.
- **Money** (`src/lib/money`) works on minor-unit strings; `parseFloat` fails lint.

## 7. The invitation renderer (`src/features/invitation-renderer/`)

Pure, safe to render on the server, light on JavaScript. Specified by
[design/GUEST_INVITATION.md](design/GUEST_INVITATION.md) and
[design/DESIGN_SYSTEM.md](design/DESIGN_SYSTEM.md).

- **Shape:** `types.ts` (the interim payload types), `schemas.ts` (lenient Zod readers for each
  block's free JSON: a malformed field is dropped, never an error), `theme.ts`, `blocks/` with
  `registry.ts`, `components/`, and `invitation-page.tsx`, which lays out the cover, the personal
  card, the letter, the footer and the reply bar.
- **Blocks:** a registry keyed by block type. The array order is kept; an unknown type renders
  nothing; a `null` or unknown variant falls back to the default.
- **Two public surfaces:** `index.ts` for components, and `index.server.ts` for the server-only
  loader, so the internal API address never reaches the browser bundle. The boundary lint allows
  exactly these two.
- **Theme:** the payload names a palette but carries no colours (BQ-1). A temporary stand-in
  (design PD-21) maps the name to roles and knows only "bordeaux"; anything else falls back. It is
  deleted when the backend sends colours.
- **The reply form** is a separate feature (`src/features/guest-reply/`) that the guest page puts
  into the RSVP block's slot through `renderReply`, so the renderer stays usable for a designer
  preview later. The route holds the saved reply and passes its summary (status, head count,
  household names) and, once sent, the "Thank you" heading back into the page.
- **The reply follows the invitation's `rsvpFields`:** a built-in question shows only when it is
  switched on, since sending a switched-off one is refused, and dietary and drink offer the host's
  own choices. Every attending member and added guest answers the host's questions for
  themselves (PD-38). `payload.ts` sends only what changed, and the page's language when it is
  not the one stored for the guest, so their confirmation and reminders follow what they read.
- **Provisional defaults** from `DESIGN_DECISIONS.md` §6 are followed in code, and named in a
  comment where the code departs from the canvas.

## 8. Styling, tokens and fonts

- `src/styles/tokens.json` is a copy of the design system's `tokens.json`.
  `npm run tokens` generates `src/styles/tokens.css` (CSS variables for the Ivory and Bordeaux
  themes) and `src/styles/theme.css` (the Tailwind `@theme` mapping and one `type-*` utility per
  type style). `npm run tokens:check` fails on drift. **The generated CSS is the source of truth
  for code**; the JSON is its input.
- **Type sizes are fluid** between 360 and 1440 px (`clamp()` in rem). `tokens.json` holds the
  desktop sizes only in each style's usage note ("40/46px on desktop"); the generator reads them
  with a strict pattern and fails the build if a note mentions desktop in other words. The
  Armenian adjustments (tracking, body line height) are in `src/styles/app.css`.
- **Components** use semantic tokens through Tailwind classes. Shared, presentational ones live
  in `src/ui/` (buttons, links, notices, form controls in `src/ui/form/`); the invitation's own in
  the renderer.
- **The app's kit** is shadcn/ui (C-14) in `src/ui/kit/`, added with the CLI from
  `components.json` and then owned by us: it passes our lint and imports our `cn` (`src/ui/cn.ts`,
  clsx with tailwind-merge). The native select, checkbox and textarea were written by hand in the
  same form, since the CLI would add `lucide-react`. The kit never imports it: the radio's dot is
  drawn in CSS, and the select's chevron and the checkbox's check come from `src/ui/icon.tsx`.
  `src/styles/app-kit.css` maps its variables onto the tokens exactly as DESIGN_SYSTEM §12
  tabulates; the CLI's own palette is not used. Its `dark:` classes stay off until a dark mode is
  designed, and its corners are square (PD-39). The invitation does not use the kit.
- **Icons** are Lucide path data copied into `src/ui/icon.tsx` with Lucide's ISC notice, rather
  than the `lucide-react` dependency, for the dozen the guest page uses.
- **Fonts:** the four Noto families as variable WOFF2, self-hosted through `@fontsource-variable`
  packages, each split into script subsets by `unicode-range`, so a page downloads only the scripts
  it uses. The stacks follow `tokens.json`: the Armenian family first, then base Noto. The Armenian
  families carry a Latin in the same design (DESIGN_SYSTEM §3.1), so Armenian, Latin and digits
  come from them; Cyrillic, `№` and `₽` fall through to base Noto. `font-synthesis: none`.
- **The invitation keeps its palette** whatever the device's dark mode (`color-scheme: light`).

## 9. Errors, headers and observability

- **Errors by status:** 400 maps to fields and the form; 401 refreshes once; 403 never retries;
  404 shows the not-found page; 409 and 429 are handled where they happen; 5xx and network errors
  show the route's error state with the request id as a reference.
- **An event the account cannot see answers 403, not 404** (`docs/BACKLOG.md` §4), so the event
  pages say "not available" for both. With no permissions endpoint (FR-6), every action is offered
  and a 403 is explained when it happens.
- **Headers** (`src/entry.server.tsx`, `src/lib/security`): a nonce-based Content Security Policy
  in production, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`. Every response for a
  path that carries a capability token (a personal invitation today), or a `?token=` query (the
  reset, email and invitation pages; `carriesCapability`), gets
  `Referrer-Policy: no-referrer`, `Cache-Control: private, no-store` and
  `X-Robots-Tag: noindex, nofollow`, applied by address in `entry.server.tsx`, so error pages and
  `.data` requests have them too. The generic link may be kept by the guest's browser for a
  minute (`private, max-age=60`), with the same referrer and robots rules. Never by a shared
  cache: every page carries its own script nonce.
- **Token links:** a page opened from `?token=` reads it once, keeps it in memory and takes it out
  of the address bar straight after hydration. It never goes into a link on the page, so the
  server's HTML does not hold it.
- **Not found:** a guest link that opens nothing (wrong, a draft, past its retention date) is a
  404 with the invitation's own not-found page, in all three languages.
- **Capability links** are redacted with the patterns of `backend/src/common/redact-url.ts`
  before anything is logged, and a test reads that file so the copy cannot drift. A payment's
  order number and an invitee's address are redacted too, though they make no page a capability
  page. Free text also loses any `token=` query value, which the client's own reset and
  invitation links carry.
- **Sentry and analytics:** none yet.

  deleting events**.
- Of an event's details: venues and the running order; its end time, side labels and per-language
